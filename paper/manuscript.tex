\begin{abstract}
Action-Effect is a versioned interchange for coupled effect descriptions bound
to captured arguments, implementation declarations, context, evidence, and
explicit coverage. We implement a finite GitHub issue-comment profile with a
JavaScript producer, a separately written Python checker, current OPA
authorization, and an occurrence-reserving dispatch gate. Its technical contract
specifies canonical preimages, ordered refusals, and read-only recovery after
uncertain delivery. Factorized measurement separates mapping, reference-input
authorization, admission, observation, task utility, and cost. The main
comparator is a complete structured adapter sharing policy, projection semantics,
and dispatch controls. Both strategies matched 108 native lane instances from
55 authored cases in 22 intent groups and all 52 eligible decisions. A controlled
live run matched 32 planned checks and created 12 comments, including four
recovered after deliberately discarded acknowledgments. Accepted-input offline
median cost was 3.97\% higher for the protocol. A separate read-only study used
an existing Azure model and the official GitHub MCP server on six maintainer
goals. In its first run, all six completed loop and schema checks.
Only one extracted Markdown body fit 6000 bytes, and none of the complete JSON
responses met the original delivery contract; review identified conflicting
harness instructions. Internal fact review marked 27 of 30 facts met, two
partial and one incorrect. An amended repeat completed two tasks and retained
four byte-budget failures; all six fully packaged repeat outputs nevertheless
fit the larger comment-profile limit. Its separate review marked 28 facts met,
two partial and none incorrect, without reclassifying failed loops.
A subsequent owned-resource study delivered the two eligible reports through
SDK and official MCP, then exercised six separate process/acknowledgment faults.
Twenty fresh workers made five comment calls; all eight duplicate probes made
none. Three delivered effects were recovered read-only, while one pre-send
interruption correctly remained unknown. Human utility remained unmeasured.
These observations show why semantic mapping, useful
output, and delivered effects need distinct evidence. The contribution is an
implemented interchange, factorized evaluation, and inspectable conditional
recovery contract, with reproducible parity, cost, and integration findings.
The evidence is same-project and bounded; provider descendants and external
validation remain outside the observations.
\end{abstract}

\section{Problem and Contribution}

A tool name does not identify every consequence, and a worrying string does
not establish a harmful occurrence. An interchange must preserve coupled
operation, resource, destination, data, quantity, applicability, and uncertainty
without confusing a declaration with authority. Existing interfaces supply
complementary facilities: MCP tool-level hints~\cite{mcp}, AuthZEN decision
exchange~\cite{authzen}, OAuth RAR permission objects~\cite{rar}, and structured
OPA/Cedar policy evaluation~\cite{opa-api,opa-lang,cedar-auth,cedar-validation}.
Action-Effect addresses description transfer and checking between native capture
and authorization, preserving these systems' responsibility for authority.

We present three implemented contributions:
\begin{enumerate}
\item \textbf{Versioned coupled interchange and finite profile.} Exact
native/context preimages, implementation declarations, evidence, quantities,
coverage and unresolved descendants cross a JavaScript/Python boundary.
Equivalent SDK and MCP captures retain distinct invocation identities while
producing the same supported direct-effect projection.
\item \textbf{Factorized evaluation with a complete baseline.} Literal mapping
references, pure authorization controls, integrated outcomes and cost distinguish
correct semantics from a decision that masks a mapping defect. Retained reports,
source pins and replay make comparisons inspectable, including failed attempts.
\item \textbf{Conditional dispatch and recovery contract.} Durable occurrence
reservation, current-policy checks, exact-ID readback and no-resend recovery have
explicit transitions, failure cuts, trust dependencies and counterexamples.
Task correctness is evaluated separately from request binding and delivery.
\end{enumerate}

The measured result is cross-language mapping parity with a small accepted-input
cost increase, controlled recovery and concrete native-integration findings.
The first real-model run also exposed an output-contract mismatch that loop and
citation checks did not detect. The amended repeat retained four task-budget
failures even though all six final comment preparations fit the native profile.
Actual delivery then preserved the two-eligible/four-withheld split; real-process
recovery retained uncertainty instead of resending.
These findings motivate the engineering question:
when does interoperable description checking justify its additional integration
and runtime cost relative to a complete direct adapter?

\subsection{Running Operation: A Maintainer's Comment}

A maintainer prepares a release-verification note for a dedicated issue. The
illustrative body \code{abc} exposes exact byte bindings. A useful report also
needs source-based checks of its technical conclusions, as the real maintainer
tasks in Section~\ref{sec:results} demonstrate.

Let $N$ be an SDK capture with lane \code{sdk}, owner \code{OndCo}, repository
\code{Action-Effect-Bench}, issue number 1 and that body. Context $C$ supplies
a principal, \code{synthetic-public} and \code{github-comment-bridge/1}.
An MCP capture nests the same parameters under \code{call.arguments} and names
\code{add_issue_comment}. The direct requested mutation is the same, but the
native JSON captures are different and should have different digests.

The checked projection binds the exact issue, constructed API endpoint, three
UTF-8 bytes and their SHA-256. It grants nothing. The direct comment is known,
while recipients, delivery and provider descendants are not observed. Suppose
current policy grants this repository/issue/class triple, permits at least
three bytes and explicitly accepts partial direct scope. The proposal can
receive allow. Revoking that policy gives deny. Retaining the grant but not
accepting partial scope gives review. Adding an executable argument makes native
input invalid; an unreadable policy is a processing failure. These outcomes
require different operator responses.

The gate reserves a caller-selected occurrence. If a successful POST's response
is lost, the requested task has not changed, but delivery knowledge has.
Assigning another occurrence and resending could duplicate the effect. The
original reservation is retained and reconciliation only reads. A matching
current object is stronger evidence than local admission, but not a complete
provider execution history.

\section{Semantic and Trust Model}

An effect is a coupled tuple of category, operation, resource, destination,
data class, quantities, and modality. A description adds the effective profile,
mapping revision, invocation/implementation/context bindings, evidence, coverage,
and explicit unresolved facts. It does not redefine the current grant or the
execution occurrence. Known, none, and unknown remain distinct. Fields from
different alternatives cannot be recombined into an unasserted permission.

\subsection{Evidence Is Not Permission}

Description processing establishes supported interpretation; a checker can
establish only the particular claim covered by its evidence and assumptions.
Authorization uses separately authenticated facts and current policy. A final
gate controls dispatch, while a provider observation covers an actual occurrence.
None of these states implies all the others. Description acceptance remains
\code{authority: not_evaluated}.

Missing required evidence withholds the affected execution but is not a
correctly recognized semantic block. An applicable trusted denial survives
unrelated uncertainty. Human review can authorize a deliberately limited scope;
it cannot make an invalid proof valid. Acceptance of a partial direct-effect
profile for one owned test resource cannot silently downgrade another policy's
requirement for complete descendant coverage.

\subsection{Conditional Guarantees and Assumptions}

If a sound checker establishes $E\subseteq U$, authority permits $U$, and
execution stays mediated under the same assumptions, covered admitted effects
respect that authority. For a policy expressible as an allowed set $B$, the
implication from $E\subseteq U$ and $U\subseteq B$ to $E\subseteq B$ is elementary.
It identifies premises an implementation must discharge; a registry signature
does not discharge them.
History, aggregate budgets, and temporal constraints are not generally
independent per-tuple membership tests. An observed trace also does not establish
a complete upper bound on possible behavior.

\subsection{Threat and Observation Boundaries}

Relevant faults include body/context/implementation drift, stale evidence,
untrusted declarations, tuple recombination, changed authority, duplicate
occurrences, and uncertain delivery. Arbitrary hidden SaaS behavior, covert
channels, and unmediated effects outside the declared universe are not covered
by the finite pilot.

\subsection{Identities and Canonical Preimages}

Define $\J(x)$ as the profile's canonical JSON UTF-8 bytes and
$\Hash(x)=\operatorname{SHA256}(\J(x))$. For an already specified byte sequence,
$\ByteHash(b)=\operatorname{SHA256}(b)$. Hashing a JSON string containing
\code{abc} is not hashing its three content bytes. The restricted core domain
rejects duplicate decoded names and invalid Unicode scalars, and supports safe
integer JSON tokens without fraction/exponent syntax. Arrays retain order,
object keys are canonically sorted, and strings are not normalized. Decision
quantities use exact decimal strings, not floating-point conversions.

Semantic action, native capture, description record, execution occurrence and
provider object are different identities. The core leaves the application's
semantic action and occurrence naming intact. Table~\ref{tab:identities} lists
the implemented bindings. Here $P$ is the full installed profile manifest.

\subsection{Conditional Invariants and Counterexamples}

These code-level invariants connect checker and gate behavior to explicit
assumptions. Each argument states its dependency and a counterexample when that
dependency is removed. The observation universe is the direct comment;
unresolved descendants remain unresolved.

\paragraph{I1: accepted-description consistency.}
Fix trusted $P$, unchanged $N,C$, deterministic projection/description functions
and correct comparison. Python \code{check} acceptance implies
\[
\J(D)=\J(\operatorname{Describe}_{P}(N,C,\operatorname{Project}_{P}(N,C))).
\]
The consumer reconstructs every expected field, including coverage, evidence
and unknowns, then compares the complete canonical values. A changed body hash
or extra array entry cannot pass merely by being well-shaped. The conclusion
is consistency with a finite installed mapping. If that mapping omits a real
webhook, two correct implementations can agree on an incomplete description.

\paragraph{I2: decision congruence under matched preparation.}
Identical complete projections, authenticated context, policy bytes and total
deterministic authorizer yield identical decisions by substitution. Parity is
therefore an expected result in this domain, not an unsuccessful security
experiment. The converse is false: different projections may produce the same
decision. The planted body-hash diagnostic gives a concrete counterexample.

\paragraph{I3: one gate-level send per reserved occurrence.}
Assume one intact shared local ledger, atomic exclusive creation, no occurrence
deletion/reassignment and complete mediation through this gate. Only the caller
creating a reservation can advance it toward dispatch, and that execution calls
\code{createComment} once. Repeated occurrences do not send. This local
at-most-one invocation property is not provider exactly-once behavior. A second
host/directory, fresh occurrence for the same task, hidden adapter retries or
provider duplication invalidates the premises or exceeds the conclusion. A
crash before POST may also consume an occurrence without useful work.

\paragraph{I4: local freshness is not remote atomicity.}
Policy is loaded after awaited identity and preflight checks. Under trusted
snapshot/policy ownership, a change completed before this load cannot be hidden
by an earlier positive decision. A revocation after the load and before remote
commit still defeats global atomicity. No additional application-level await is
needed for that race; local sequencing does not create a distributed transaction.

\paragraph{I5: reconciliation creates no new write.}
The recovery routine prepares, loads the ledger and reads the provider. It has
no create branch. With genuinely read-only provider methods it cannot resend.
It also does not request a new write grant: observing prior delivery differs
from authorizing another effect. Read authorization remains the caller/provider's
responsibility. A malicious read adapter or operator rerun is outside the routine.

\paragraph{I6: two strengths of current confirmation.}
A known ID plus exact ID/API URL/issue URL/body/actor checks establishes matching
current direct content. Without an ID, complete preflight and one exact match
with a new ID establish new current content since preflight, not which execution
caused it. A same-account writer posting identical bytes defeats attribution
without defeating equality. This motivates the explicit ID-less qualifier
\emph{not execution attribution} rather than a stronger causal claim.

Control-flow arguments do not supply missing trust, completeness, currentness,
durability or provider semantics. Set containment cannot establish those premises.

\section{Relation to Existing Interfaces}

\subsection{MCP Tool Annotations}
The selected \code{2025-11-25} schema includes read-only, destructive,
idempotence, and open-world hints, with an explicit warning against trusting
annotations from untrusted servers~\cite{mcp}. It is not asserted to be the
latest revision or the protocol actually negotiated in a run. A supported
effect extension needs its own agreed semantics; there is no claim of an
upstream-standard Action-Effect field. A capable MCP integration can already
use a context-aware structured adapter, so hints-only comparison is insufficient.

\subsection{AuthZEN and OAuth RAR}
AuthZEN Authorization API 1.0 is Final, published 11 January 2026, and provides
subject/action/resource/context decision exchange~\cite{authzen}. Its successful
decision is boolean with optional context. Review, unsupported semantics, and
processing failure need explicit application-level mappings, not invented
boolean values or automatic correctness credit for a failed PDP call.

RAR's structured \code{authorization_details} and separate objects preserve
distinct permission combinations. RFC 9396 section 6.1 explains that arbitrary details
lack a universal comparison operation independent of type semantics~\cite{rar}.
Requested details, granted details, and described effects are different.
Token privilege restriction, audience checks, and actual resource authorization
remain necessary~\cite{oauth-bcp}. Reusable evidence does not cache permission.

\subsection{Complete Structured OPA and Cedar Adapters}
OPA accepts complete structured input. Its Data API can return HTTP 200 without
a \code{result} for an undefined document, while built-in errors ordinarily
evaluate to undefined unless the selected strict-error mechanism changes that
behavior~\cite{opa-api,opa-lang}. The required total-decision wrapper must
validate outputs and declare its error configuration identically across arms.

Cedar provides principal/action/resource/context requests, entities, policies,
and schema validation. Its documented default-deny, forbid-overrides-permit,
and skip-on-error semantics return diagnostics; an error in one policy can
coexist with an Allow from another~\cite{cedar-auth,cedar-validation}. That is
not automatically a Cedar defect. A stricter wrapper or review route must be
explicit and symmetric. Policy validation does not authenticate facts. Cedar
is a future comparator, not an executed lane of the current OPA pilot.

\subsection{Provenance, Digests, and Provider Semantics}
PROV-DM structures provenance but does not establish factual truth~\cite{prov}.
JCS defines canonical JSON, not authority or semantic correctness~\cite{jcs}.
The finite consumer's numerical subset must not be presented as full
binary64/JCS support. GitHub documents notification effects and secondary rate
limiting for comment creation~\cite{github-comments}. Recipients, delivery,
webhooks, and other descendants remain unresolved under the partial profile.
Reading a comment does not establish their absence. HTTP retry semantics
likewise do not make an uncertain create safe to repeat~\cite{http}; a local
marker or MCP hint is not a provider idempotency key.

The comparison unit is a boundary responsibility. A decision API need not infer
effects, an effect schema need not issue tokens, and a policy engine need not
inspect remote code. Table~\ref{tab:related} makes the application obligations
explicit instead of penalizing a component for another component's job.

The additional surface is agreement on description preimages, applicability,
coverage, unknowns and rejection semantics. A direct adapter can retain those
facts internally. The research question is whether portability reduces duplicated
integration work or exposes errors across implementations. This pilot measures
preservation and cost, not maintainer hours saved, and cannot isolate benefits
of this wire format from typed contracts generally.

A stronger future baseline could export its own complete typed record under an
equally explicit contract. It must not be deprived of hashes, context or failure
reasons. If preservation remains equal, governance, migration burden and consumer
availability may decide adoption rather than safety or speed.

\section{Bounded Runtime Pilot}

The published \href{https://github.com/OndCo/Action-Effect-Spec/releases/tag/v0.2.0-draft.1}{Spec prerelease \code{v0.2.0-draft.1}}
resolves to \href{https://github.com/OndCo/Action-Effect-Spec/commit/a9b86f4b529a5e330c2a9bf1b8c4c259a7b36e40}{\code{a9b86f4}},
pinned in Bench's \path{spec-lock.json}. The measured Bench source is
\href{https://github.com/OndCo/Action-Effect-Bench/commit/9f638df994504ba6f5d82c0b5409922a0be7a72e}{\code{9f638df}}.
GitHub Issue Comment Profile 1 is additive on
unchanged core wire version \code{0.1.0-draft.1}; its released source is
\path{profiles/github-issue-comment/README.md}. Native SDK input contains
owner, repository, issue number, and body; the MCP lane uses
\code{tools/call} for \code{add_issue_comment}. Lane-specific capture envelopes
are not a replacement MCP protocol. Equivalent intents compare checked
projections, not full description digests that include different native lanes.

Reports record MCP SDK \code{1.32.1}, Octokit \code{22.0.1}, OPA
\code{1.21.2}, Node \code{22.18.0}, and Python \code{3.9.6}, with source and
binary hashes. Offline evaluation uses local SDK/MCP-shaped captures and real
OPA, not provider transport. The live MCP lane uses official SDK stdio
initialize/list/call against the benchmark-authored
\code{action-effect-comment-pilot} server, not GitHub's official MCP server.
Both live lanes use Octokit against GitHub.

The profile binds the exact issue and destination to body SHA-256 and UTF-8
byte count. Its finite input domain includes a nonempty Unicode-scalar body
of at most 8192 bytes. Data classification is trusted configuration, not DLP;
\code{github-comment-bridge/1} is a checked declaration, not attestation of
provider code. Success is \code{accepted_partial/declared_partial}, still
without authority. After applicable denials, the experiment policy requires
\code{allow_partial_direct: true}; otherwise partial scope requires review.

The protocol arm uses producer, description, separate consumer, real OPA, and
a final gate. The main baseline substitutes a complete structured adapter but
shares policy, authenticated facts, gate, occurrence ledger, observation rules,
and offered work (Figure~\ref{fig:factorization}). A lossy-field ablation is not
the main competitor. Only approved synthetic operations on owned public test
issues may be dispatched; a stub or replay cannot count as live evidence.

\subsection{Profile and Registry Lifecycle}

The installed profile is a finite semantic program defined by a manifest and
versioned rules. Repository release, core wire, processing contract, mapping
revision, implementation declaration and executable versions are distinct.
Release \code{v0.2.0-draft.1} did not change core \code{0.1.0-draft.1};
opt-in \code{offline-consumer-v1.1} clarifies legacy refund processing without
rewriting its frozen contract or examples.

The comment manifest fixes lanes, operation, path-safe identities, limits,
namespaces, local references, critical extension and unknown scope. A received
URI cannot select arbitrary code. The Python consumer independently reconstructs
the expected description instead of importing the producer or trusting its
proposed projection.

The core requires immutable meanings and explicit experimental, stable,
deprecated or withdrawn states. Changes to conditions or evidence rules require
new identities. Withdrawal must not substitute bytes under an old revision:
sensitive payloads may become unavailable with safe tombstones rather than
remaining public just to preserve a digest. This is a lifecycle obligation, not
an implemented signed registry or tested key-rotation service.

Cached bytes and cached acceptance are different. A document may remain readable
while trust, context or evidence is stale. Acceptance reuse would bind full
description, profile/mapping/checker revisions, implementation, trust epoch and
dependencies. The pilot uses cold checking, not a persisted acceptance cache.
Python memoizes only its installed profile within a process. Neither a record
hash nor the occurrence ledger is permission reuse.

\subsection{Ordered Native and Description Checking}

Owner names are ASCII/path-safe, at most 39 characters. Repository names are
path-safe, at most 100 characters, excluding dot and dot-dot segments. Issue
numbers are positive integers at most 2147483647, not booleans or coerced strings.
Bodies are nonempty Unicode-scalar strings of at most 8192 UTF-8 bytes. Whitespace
and escaped NUL are preserved. Arbitrary endpoints, percent-decoding, templates
and executable expressions are outside the profile.

\par\noindent\begin{minipage}{\linewidth}

\begin{lstlisting}

Precedence is externally visible. Invalid native shape precedes context checks;
another shaped MCP tool is unsupported without interpreting its arguments as a
comment. Missing context and a different declared implementation have distinct

arbitrarily large integer allocation. Native validation classifies those and
native scalar defects as \code{native_input}. Accepted inputs are reparsed from
the original bytes under the strict core parser before hashing. Preliminary
values never become digest preimages. This preserves the frozen core rules while
repairing the first run's native-error precedence mismatch.

\section{Falsifiable Questions and Experimental Design}

\code{PROTOCOL.md} governs the study; this paper does not silently change its
corpora, labels, scoring, or independence requirements.

\begin{enumerate}
\item \textbf{Meaning preservation:} do both arms match reference coupled
effects, binding state, and uncertainty across equivalent intents? Baseline
parity supplies no added mapping benefit; extra loss or unsupported outcomes
count against the proposed interchange.
\item \textbf{Diagnostic value:} can separate mapping, reference-input
authorization, and integrated scores reveal policy-masked mapping defects?
Report their joint correctness cells, with additional explicit failure cells.
A complete baseline may expose the same distinctions.
\item \textbf{Unknowns and freshness:} do prewritten drift, authority-change,
capability, and delivery cases preserve required limits? Fabricated known facts,
stale acceptance, error-as-review, and permission reuse contradict the contract.
\item \textbf{Cost and utility:} does any demonstrated portability or protection
benefit justify complete cost, withheld work, intervention, and recovery?
Negative findings and a better baseline remain valid outcomes.
\end{enumerate}

remain additional states, not forced into a binary success table. A wrong
mapping with a correct-looking downstream denial belongs to the third cell.

\section{Scope and Validity}

\paragraph{Semantic coverage.}
The mutation profile covers one direct GitHub comment. Notifications, recipients,
webhooks and other descendants remain unknown; accepted mappings are partial.
The original live data were synthetic public inputs. Real-model maintenance
adds bounded reading/report generation, not profile-governed arbitrary reads.
Publication-fit preparation does not dispatch; the distinct owned-write
continuation in Section~\ref{sec:owned-write} observes official-server mutations
through the same finite direct-comment profile. Its deliberate faults are not
naturally observed outages.

\paragraph{Trust and concurrency.}
The host, configured principal/class, provider adapter, policy files and same-host
ledger are trusted. Bridge identity is declared, not SaaS attestation. Invariants
are code-level arguments, not machine-checked whole-system proofs. Policy reload
is not atomic with remote commit. ID-less recovery requires complete preflight,
unique new content and a dedicated single writer; another same-account writer
defeats attribution. Hashes and replay establish specified consistency, not
operator honesty, historical fsync or distributed exactly-once delivery.

\paragraph{Sampling and independence.}
Shared policy, contracts, project control and AI-assisted authoring/review permit
correlated errors. Separate consumers and references are checks, not independent
institutions. External independently authored evaluations number zero. The six
maintenance goals use the project's exposed public sources; post-review repeats
remain exposed follow-up work, not holdouts. A rubric requesting human review
does not establish that it occurred; actual review provenance is reported.

\paragraph{Inference and deployment.}
Small sequential cold timings support their samples, not throughput, tail-SLA,
staffing or monetary claims. Different SDK/MCP task goals are not paired speed
observations. Loop completion, citation availability, quality, decision readiness,
actual use and delivery are distinct endpoints. Related work compares concrete
interface obligations rather than surveying all effect systems or authorization
theory. Customer qualification and long-duration benefit need additional evidence.

\subsection{Case Analyses: What Aggregates Hide}

The Unicode cases test byte semantics, not natural-language correctness.
\code{unicode-nfc} and \code{unicode-nfd} preserve distinct precomposed and
decomposed bytes. A four-character cafe spelling with an accented final letter
occupies five UTF-8 bytes: a five-byte policy limit permits it and a four-byte
limit denies it. The native cap instead accepts 8192 bytes and rejects 8193
before policy. These are different obligations; a native-domain error is not
credited as a correct current-policy denial.

The tuple cases distinguish cross-repository/issue and cross-class recombination
from an exact grant among decoys. The first two deny despite individual field
matches; the third allows because one whole row matches. A deny-everything
system fails the positive control. Case-sensitive owner/repository variants
are mapped literally and denied against differently cased grants, not normalized
through guessed provider aliases.

Precedence cases combine revocation, absent grants or excessive bytes with
unaccepted partial scope. Known denials win over review. The otherwise permitted
partial-scope case still receives review, while missing context or a wrong
implementation produces untrusted evidence before authorization. These tests
check refusal ownership, not simply non-execution.

The first scorer defect compared language-object prototypes instead of JSON
values and reported 52 apparent masked errors per arm. Correcting comparison
exposed eight genuine structured numeric/Unicode classification mismatches.
Those mattered to interoperability even though they did not grant unsafe work.
All 216 original input/context/policy/expected records remained unchanged. The
lesson is to specify comparison and precedence, not erase failure history or
claim repair of 52 dangerous defects.

The live duplicate reused the earlier ASCII occurrence: its suppression is not
a second denial or an extra object. The ACK-loss scenario first completed a real
POST and deliberately discarded its successful response. Recovery therefore
has a controlled injection witness as well as weaker current-content evidence.
Conflating those would generalize the result to arbitrary unwitnessed timeouts.

\section{Conclusion}

Action-Effect makes native capture, coupled meaning, evidence, current authority
and observation explicit and executable. The v0.2 results establish exact
mapping/decision parity, controlled read-only recovery and 3.97\% higher

\section{Compatibility and Deployment Decisions}

Before adding a domain, define capture, exact quantity/identity semantics,
permitted context acquisition, evidence reference rules, supported scope and
required unknowns. Implement an independent consumer and a competent direct
adapter. Arbitrary JSON keys or unknown-URL resolution do not make a profile
generic.

Migration checks wire, profile, processing contract, installed implementation
and policy separately. Unknown critical semantics require refusal, not removal
and retry. An unavailable old revision cannot be interpreted under new rules
without changing the claim. Historical reports name their executed versions.

Product use requires measured support for actual domains, credentials, durable
ownership, operator recovery and task utility. The synthetic-public experiment's
partial-direct exception cannot satisfy a customer's complete-descendant policy.
The one-host ledger also needs replacement or qualification before multi-host
use. These are engineering acceptance criteria, not permissions silently
created by a public manuscript.
