## Deliverables and verification

1. **Requirement accountability and candidate pin.** In Spec, map each of
   CORE-001 through CORE-028 to roles, bounded implementation support, actual
   positive/negative evidence and remaining gaps. Machine-check the inventory
   and local references. Freeze the existing GitHub issue-comment profile's
   normative components in an additive, digest-checked candidate manifest.
   Do not reinterpret historical profile identifiers or claim full core
   conformance from a file inventory check.
2. **Report contract preflight.** In Bench, add an opt-in third field-study
   edition. Preserve the six tasks, pinned sources, 6000-byte Markdown limit,
   model configuration, complete traces and all previous results. Offer a
   local, side-effect-free draft check with exact byte count, schema and
   observed-source feedback. The model may explicitly revise inside the same
   fixed task budget, not silently retry a failed final answer. Keep initial
   draft acceptance, final completion, cost and usefulness separate.
3. **Failure composition.** Test oversized drafts, changed final content,
   unknown citations, input attacks, exhausted budgets, evidence journal
   failures and fresh-task state isolation. Reuse existing grant/ledger
   invariants and test compounded revocation, uncertain completion and
   duplicate/recovery conditions without authorizing a repeat send.
4. **Adopter handoff.** Provide an actionable entry point for implementing the
   pinned candidate without OSuite, a support declaration and an external
   evaluation checklist. Keep mapping, authorization, provider outcomes and
   useful task completion distinct. No external implementer or partner is
   presumed confirmed. A second platform profile requires an agreed real
   workflow and separately scoped effects.
5. **Verification and evidence.** First run red/green regressions for new
   behavior; then both consumer suites, offline corpus comparison, runtime
   suites, field suites and historical replay. If existing configured model
   credentials and official read-only MCP are available, freeze the new
   runtime before one scheduled six-task attempt, retain every failure and
   publish a separate replayable report. No repeated trial selection to obtain
   a preferred score.

## Release decision

Internal implementation can finish without an external collaborator, but the
stable-release gate remains closed until independently implemented applicable
requirements and separately governed evaluation are demonstrated. Do not
deploy a product or label the historical manuscript updated by this round.

The close-out must distinguish completed engineering, experimental results,
unmeasured usefulness, unresolved trust/authority obligations and external
dependencies. No single total test count substitutes for that separation.
